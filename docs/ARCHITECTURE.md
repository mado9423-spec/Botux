# المعمارية

## فصل المسؤوليات

```
                 ┌────────────── بيانات السوق العامة (GET فقط) ──────────────┐
                 │  data/market.py: جلب + تحقق (تكرار/ثغرات/OHLC/قِدَم)        │
                 └───────────────────────────────┬──────────────────────────┘
                                                 ▼
 strategy/  ──►  runner.py (الحلقة)  ──►  risk/manager.py  ──►  execution/order_manager.py
 (إشارة فقط)     دورة واحدة كل poll       حجم الصفقة + السقوف        كتابة مسبقة + معرّف حتمي + تسوية
                       │      ▲                                              │
                       │      └── ledger.py (ما يملكه البوت فعلاً)             │
                       ▼                                       ┌────────────┴────────────┐
              killswitch / alerts / storage                    ▼                         ▼
                                                     execution/paper.py        execution/live.py
                                                     (محاكٍ بلا شبكة)          (مقفل بحاجز safety.py)
                                                                                         │
                                                                              exchange/client.py (قائمة بيضاء)
```

| المكوّن | الملف | مسؤوليته الوحيدة |
|---|---|---|
| بيانات السوق | `data/market.py` | تحويل الشموع إلى `Decimal` والتحقق منها؛ إسقاط الشمعة غير المغلقة؛ اكتشاف البيانات القديمة |
| الاستراتيجية | `strategy/*` | `on_candles(شموع مغلقة، هل في مركز؟) → إشارة`. لا تعرف المال ولا الأوامر |
| دفتر البوت | `ledger.py` | رأس مال البوت = `risk.bot_capital` + أثر **تنفيذاته المسجّلة**؛ ما يملكه من عملة الأساس؛ متوسط تكلفة المركز؛ كشف الفرق عن أرصدة الحساب |
| المخاطر | `risk/manager.py` | حساب الكمية (تقريب للأسفل دائماً)، السقوف عند أسوأ تنفيذ، حد الخسارة اليومية (يدوي الرفع)، **عوائق الدخول** (blockers)، البوابة الأخيرة قبل الأمر |
| قواعد المنصة | `exchange/rules.py` | تحليل `exchangeInfo`، تقريب السعر/الكمية، PRICE_FILTER/LOT_SIZE/MARKET_LOT_SIZE/NOTIONAL/PERCENT_PRICE (وMAX_POSITION للإبلاغ) |
| مدير الأوامر | `execution/order_manager.py` | الإرسال، حالات الأمر، التسوية، منع التكرار، حارس الدخول الأخير، إعادة الاستعلام عن الضائع |
| المحاكي | `execution/paper.py` | تنفيذ وهمي بنفس فلاتر المنصة والرسوم والانزلاق؛ تنفيذ جزئي وأعطال تُحقن للاختبار |
| الموصل | `exchange/client.py` | HTTP + التوقيع + حدود الطلبات + قائمة النقاط المسموحة (لا سحب/تحويل/هامش/عقود) |
| الحاجز | `safety.py` | شروط التفعيل الحقيقي وفحص صلاحيات المفتاح |
| البروفة | `execution/livecheck.py` | `live-check`: قراءات + `order/test` فقط (عميل لا يستطيع إرسال أمر) |
| الإيقاف | `killswitch.py` | ملف + علم في الذاكرة؛ لا يُزال تلقائياً؛ يتحقق من قابلية الكتابة |
| التخزين | `storage.py` | SQLite: أوامر، تنفيذات، أحداث، حالة، منحنى رأس المال؛ معاملات ذرّية |
| الحلقة | `runner.py` | تنسيق الدورة وإدارة الأخطاء والإيقاف |

## دورة واحدة (`TradingLoop.run_cycle`)

1. هل الإيقاف الطارئ مفعّل؟ ← تسوية ما في الطريق، إلغاء أوامر البوت المفتوحة، بيع المركز **فقط** إن كان `flatten_on_kill`، تنبيه بكل مركز/أمر
   غير محسوم، ثم التوقف.
2. إعادة فحص حاجز التداول الحقيقي (حي فقط): ملف التسليح، بصمة الإعدادات، **إعادة قراءة ملف الإعداد من القرص**، ملف الإيقاف، وصلاحيات المفتاح
   (كل ساعة؛ فشل الفحص يُعاد بعد دقيقة ويغلق الحاجز بعد 10 إخفاقات). إغلاقه ⇒ عائق دخول **غير مخزَّن** (لا يمتد إلى إعادة التشغيل).
3. فحص صحة: قاعدة البيانات قابلة للكتابة؛ إعادة قراءة `exchangeInfo` عند حلول موعدها (فلاتر + حالة الرمز).
4. تسوية الأوامر غير المؤكدة/المفتوحة (`reconcile_pending`)، وإعادة استعلام بطيئة عن الأوامر الضائعة.
5. جلب أسعار العرض/الطلب **لكل رمز على حدة** (فشل رمز لا يُسقط البقية)؛ فحص الأوامر المفتوحة على المنصة (أي أمر ليس من البوت ⇒ عائق دخول)؛
   بناء صورة المحفظة **من دفتر البوت**؛ مقارنة الأرصدة بالدفتر (فرق غير مفسَّر ⇒ عائق دخول)؛ تحديث حد الخسارة اليومية وتنفيذ طلبات الإقرار البشرية.
6. **الحماية أولاً:** وقف الخسارة البرمجي لكل رمز، من السعر والأرصدة فقط **دون الاعتماد على الشموع**، ولا يمنعه أمر شراء غير محسوم
   (يمنعه بيع غير محسوم أو ضائع، لتفادي البيع مرتين). الخروج الذي لم يُنفَّذ كاملاً (صفر أو جزئي) ينتج تنبيهاً حرجاً.
7. ثم **الحفظ** (حالة المخاطر، منحنى رأس المال): بعد الحماية، فلا يستطيع قرص ممتلئ تخطّي وقف خسارة.
8. ثم الإشارات: جلب الشموع المغلقة والتحقق ← أول دورة في **كل عملية** تسجّل الشمعة ولا تتداول ← شمعة **أحدث** من آخر معالَجة: إشارة ← عمر الإشارة
   مقبول؟ ← فارق السعر مقبول؟ ← حجم ← بوابة المخاطر ← **حارس الدخول الأخير** (البوابة الحقيقية + حالة المخاطر من جديد) ← أمر.
   مشاكل الشموع تعني «لا إشارة الآن» (حدث `no_signal` وتنبيه بعد 3 دورات) ولا تُحتسب نحو الإيقاف الطارئ.
9. قرار واحد على الأكثر لكل شمعة، إلا الأوامر التي ثبت أنها لم تُرسل (لا اتصال/انحراف ساعة/حد طلبات) فتُعاد حتى 3 مرات.
10. الإيقاع ثابت: زمن الدورة نفسها يُخصم من فترة الانتظار.

## آلة حالات الأمر

```
            ┌──────────────► REJECTED   (رفض قطعي: لم يُنفَّذ)
 PENDING_SEND ──► NEW ──► PARTIALLY_FILLED ──► FILLED
      │                │                          CANCELED / EXPIRED (قد يكون بتنفيذ جزئي)
      └──► UNKNOWN ────┘   (مهلة/5XX/‎-1007: ربما نُفِّذ)
              │
              └─ استعلام بالمعرّف ─► يتبنّى حالة المنصة (+ التنفيذات الحقيقية من myTrades إن غابت)
              └─ لم يوجد بعد N محاولات ─► LOST (+تنبيه حرج؛ الرمز محجوب للدخول، والبيع الضائع يحجب بيعاً آخر)
                                          └─ إعادة استعلام كل بضع دقائق: إن ظهر يُتبنّى ويُرفع الحجب
```

نتيجة `submit`: `accepted` (نُفِّذ أو يستقر على الدفتر) | `not_filled` (ردّت المنصة بلا تنفيذ) | `partial` (تنفيذ جزئي وانتهى) | `duplicate` | `blocked` |
`rejected` | `retry_later` (لم يُرسل قطعاً) | `uncertain`.

الأخطاء المفضية إلى `UNKNOWN`: مهلة، 5XX، ‎-1000/‎-1001/‎-1006/‎-1007/‎-1008، 408/499، أي استجابة بلا جسم Binance مفهوم (HTML من وسيط)،
200 غير قابلة للقراءة. أما `-1021` وحدود الطلبات وعدم الاتصال فتعني «لم يُرسل قطعاً» ← يُحذف السجل ويُعاد المحاولة لاحقاً.

ضمانات: الإدخال في قاعدة البيانات **قبل** الإرسال؛ `client_order_id` حتمي = `bx` + 30 خانة من SHA-256 لمفتاح النية
(استراتيجية:رمز:شمعة:اتجاه) فلا يتكرر الأمر عبر إعادة التشغيل؛ **لا إعادة إرسال تلقائية أبداً** (الإلغاء والقراءات فقط تُعاد لأنها متساوية الأثر)؛
سجل الأمر وتنفيذاته (وحجب الضائع) تُكتب في **معاملة واحدة**؛ التنفيذات تُسجَّل مرة واحدة مهما تكررت التسوية.

## لماذا الاستطلاع لا WebSocket؟

أبسط وأسهل في التحقق والاختبار ويكفي لشموع ≥ 15 دقيقة. الثمن: تأخر الاكتشاف بمقدار فترة الاستطلاع. تدفق بيانات المستخدم
(User Data Stream، وهو الآن عبر اشتراك WebSocket API في وثائق Binance) تحسين مستقبلي لتقليل الاعتماد على الاستعلام؛ وحتى إن وُجد فغياب الحدث
منه **ليس دليلاً** على عدم التنفيذ، فيبقى الاستعلام بالمعرّف هو المرجع.
